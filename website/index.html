A restaurant register that runs on your own server.

Tables, kitchen workflows, inventory and online pickup — with orders, receipts and backups persisting on hardware you control. No cloud subscription, no forced login, no merchant database on a third-party server.

Capabilities

Front of house to back office

💵

Cash sales & returns

A SQLite transaction journal committed atomically with stock movements — money and inventory move together.

🍽️

Tables & kitchen workflow

The dine-in service loop: open a table, take the order, run it through the kitchen, close out.

📦

Inventory, automatic

Stock levels update from every completed transaction, without a separate bookkeeping step.

🛵

Online pickup requests

Customers queue pickup orders through a flow that feeds the same register and journal.

👥

Staff action permissions

Per-role controls enforced server-side — not a cosmetic UI toggle.

🔍

Owner-only order history

A searchable history of every transaction, visible only to the owner.

📊

Business-date CSV reports

Custom reports aligned to your business date for day-end and back-office use.

💾

Encrypted backup & recovery

Backups include the transaction journal and restore the complete register state.

Architecture

Next.js UI, Hono API, SQLite on your machine

Next.js 15 UI React 18 + Tailwind→ Hono API Cloudflare Workers runtime→ SQLite + Drizzle ORM transaction journal | REST + WebSocket→ 127.0.0.1:8787 loopback only→ encrypted backups

Same foundation as the sibling pos-retail, tuned for dine-in: the kitchen workflow and online pickup are the differentiators; the co-hosted retail register keeps cash, inventory and journal semantics intact.

Run it

Four commands to your own register

Quick start

git clone https://github.com/honeyamn10-source/pos.git
cd pos
pnpm install --frozen-lockfile     # Node 20 LTS / pnpm 9+
pnpm run build:server
pnpm run start:server

Open http://localhost:8787 and use data/setup-token to create your owner account. No default password exists.

Security

Security posture you can verify in the repo

🪙

No default passwords

The owner account is created from a secure setup token. There is no admin/admin backdoor.

🔒

Server-side enforcement

Sessions and staff permissions are enforced on the server, not hidden in the UI layer.

🔌

Loopback-only serving

The register binds to 127.0.0.1 by default; expose it only when you mean to.

🧹

Clean repository surface

No secrets or private hosting identifiers are committed.
